Start here

  • Explain how firewall rules, zones, and connection state control traffic.
  • Trace traffic through a firewall rule and a NAT or port-forward mapping. Distinguish HTTP, SSH, and ICMP ping.
  • Explain vulnerabilities and CVEs, how scanners find possible issues, and why findings require verification.

Week 36 Firewalls

Purpose and rule decisions

A firewall enforces a network security policy by permitting or blocking traffic at a boundary or between zones. Rules can match interface, direction, source and destination addresses, protocol, and ports, and may log the decision. A zone groups interfaces or networks with a common trust level. A DMZ isolates systems requiring external access from the internal LAN, limiting paths available if a server is compromised.

The lecture describes first matching rule behavior. Read rules in the actual configured order and note the default action and product-specific floating or quick rules. A broad earlier match can prevent a later rule from being reached. A rule allowing LAN to Internet need not allow LAN to DMZ, and permission for TCP port 80 does not automatically allow ICMP echo.

Stateless stateful and application aware filtering

A stateless filter evaluates each packet using fields such as addresses, protocol, and ports without remembering a flow. A stateful firewall tracks connection state and can recognize return traffic belonging to an allowed connection. Both depend on policy and correct routing. A next-generation firewall may add application identification, deep inspection, IDS/IPS, URL filtering, identity-based access, and threat intelligence.

Port numbers are hints, not proof of application identity. In Lab 1 SSH was deliberately configured on TCP 8080: a port-based allow rule could permit SSH even though 8080 is often associated with web traffic. Application-aware inspection can distinguish protocols when it has adequate visibility. Encryption can limit inspection; TLS inspection has privacy and deployment implications. SSH and TLS are different protocols.

NAT PAT and port forwarding

Network address translation changes IP addresses in packets. Static NAT maps an address consistently; dynamic NAT draws from a pool; PAT multiplexes many connections using ports. NAT conserves addresses and obscures internal addressing but does not replace firewall policy. Port forwarding translates inbound destinations: for example, WAN-IP:52314 to 10.1.0.150:22. External and internal ports can differ. A matching WAN rule, route, listening service, and host firewall policy are also necessary.

For the lab HTTP example, a WAN TCP request to the firewall WAN address on port 80 is redirected to the DMZ server on TCP 80. Test from the intended source after applying the rule. A successful internal test alone does not establish external access.

Other features

  • VPN provides encrypted remote access to an organizational network.
  • IDS detects suspicious traffic; IPS can also block it. Detection is not perfect.
  • A WAF examines web application traffic for threats such as injection; it complements network filtering.
  • Logging helps explain which rule matched; URL filtering controls sites; traffic shaping manages bandwidth and quality of service.
  • OPNsense is the FreeBSD-based firewall and router used in the lab, with NAT, VPN, segmentation, and optional IDS/IPS features.

Week 37 Vulnerabilities

From weakness to risk

A vulnerability is a weakness that can be exploited. A threat is a potential cause of harm; an exploit is a method or code that takes advantage of a weakness; risk depends on exposure, likelihood, and impact. SQL injection targets unsafe handling of database queries; cross-site scripting (XSS) injects script into a web context; a buffer overflow can corrupt memory when input exceeds a buffer's safe handling. Consequences include data exposure, service disruption, and system compromise.

Detection methods and limits

  • Automated scanning: Nessus, OpenVAS, and Qualys compare observable conditions with known checks. They scale well but can miss issues or report false positives.
  • Manual penetration testing: authorized testers investigate attack paths and business context; depth depends on scope, time, and access.
  • Static analysis and code review examine source without executing it; examples include SonarQube and Checkmarx.
  • Dynamic analysis and fuzzing exercise running software, including unexpected inputs, to expose runtime flaws.
  • Dependency inventory and an SBOM record third-party components and versions for comparison with known issues. OWASP Dependency-Check is an example.

A CVE is a standardized identifier for a publicly disclosed vulnerability. It identifies the issue; it is not itself a severity score, proof of exploitation, or proof that your installation is affected. Check the asset, version, configuration, exposure, and vendor guidance. CVSS is a severity scoring framework; a score alone is not a full risk assessment. CWE classifies types of weakness; CAPEC describes attack patterns; OWASP Top 10 highlights major web application security risks. DevSecOps integrates security into development and operations.

Zero Trust

Zero Trust assumes network location alone is insufficient for trust. Verify explicitly using identity and context, grant least privilege, and assume breach. Apply MFA and identity controls, assess device health, segment resources, monitor activity, and protect data. Microsegmentation restricts lateral movement between workloads; it does not guarantee that an attacker cannot move. Continue to authenticate and authorize relevant access requests.

Case study lessons from the lecture

  • Equifax: unpatched Apache Struts vulnerability. Maintain an inventory, prioritize exposed assets, patch, and verify deployment.
  • SolarWinds: malicious code in Orion updates. Protect build and update supply chains and limit trust granted to management tools.
  • Colonial Pipeline: compromised credentials for legacy VPN access. Strengthen remote access, remove unused accounts, require MFA, and prepare incident response.
  • Target: compromise through a vendor. Restrict third-party access, segment networks, and monitor vendor activity.
  • Capital One: cloud firewall misconfiguration. Review cloud access paths and permissions, monitor configurations, and limit breach impact.

Lab 2 Scan interpretation

The lab uses deliberately vulnerable containers on the DMZ host. Docker -p HOST:CONTAINER maps a host TCP port to a container port: 8010:80 exposes container HTTP at host port 8010; 8022:22 exposes container SSH at host port 8022; the second target maps 8080:80. Use these only on authorized systems. Validate results before remediation: a banner can be inaccurate, and a scan can produce false positives. Week 38 PKI and certificates

PKI trust and keys

Public key infrastructure (PKI) manages certificates, public and private keys, issuance, and revocation. A certificate authority (CA) signs a certificate binding a public key to an identity. A registration authority (RA) verifies requesters for the CA. A trust store contains trusted roots; validation builds a chain from the server certificate through any intermediate CA to a trusted root. A compromised root can undermine every certificate trusted through it.

The private key stays secret and proves control through a signature; the public key verifies signatures. Depending on the scheme it can also be used for encryption. A certificate is public and includes subject, issuer, public key, validity, and typically Subject Alternative Names (SANs) and usage constraints. Extended key usage (EKU) indicates purposes such as server authentication, client authentication, code signing, or email protection.

To validate an HTTPS certificate, check chain signatures and trust, validity period, intended usage, matching hostname in SAN, and revocation status according to client policy. A CRL is a published list of revoked certificates; OCSP is a protocol for checking status. Revocation may matter when a key is compromised before the certificate expires. A valid certificate alone does not prove the site or its content is safe.

Domain validation (DV) checks control of a domain; organization validation (OV) adds organization checks; extended validation (EV) involves additional checks. A self-signed certificate can encrypt traffic but is not automatically trusted. A warning may indicate an untrusted issuer, incorrect name, expired certificate, incomplete chain, or other failure; investigate rather than bypass it.

Lab 3 workflow and mutual TLS

1. Generate a server private key and CSR. The CSR contains the public key and identifying information, and is signed using the private key. It does not contain the private key.

2. The lab's OPNsense CA signs the CSR. Install the server certificate and matching private key on Apache; configure the CA chain as needed. The lab maps the test name to the DMZ address in the client hosts file and uses the matching DNS SAN.

3. Trust the lab CA on the relevant client and verify the chain. Trust stores vary by application and configuration. Trusting a root gives it broad authority, so only trust a verified CA.

4. Harden the lab server to TLS 1.2 and 1.3, then require a client certificate with SSLVerifyClient require. In mutual TLS (mTLS), the client authenticates the server and the server also validates a client certificate. A client certificate and corresponding private key can be distributed in a protected .p12 file.

The completed quiz showed a missing required client certificate error: SSL_ERROR_RX_CERTIFICATE_REQUIRED_ALERT. Your answer was manually corrected by the teacher. This is specific to the lab and browser, not every TLS failure. Useful commands from the lab include openssl req -in request.csr -noout -text and openssl verify -CAfile CA.crt server.crt. Chain verification alone does not test every browser hostname and policy check.

Week 40 Logging

A log records an event and its context, commonly time, source, actor, action, outcome, and relevant process or network details. Logs support operational troubleshooting, detection, forensic timelines, and audit. Key sources include Windows Security/System/Application, Linux journal and auditd, authentication services, firewalls, proxies, IDS, and application logs such as Apache access_log and error_log.

Plan what to collect, why, access controls, retention, and integrity. A common pipeline is generate, collect, parse or normalize, store, analyze, alert, and report. Synchronize clocks and preserve time zones; missing, manipulated, unparsed, or late logs can mislead investigators. The lecture uses six months as an illustrative retention guideline, not a universal rule: actual retention depends on purpose, privacy, obligations, and organizational policy. Minimize personal data and restrict access.

Week 41 SIEM

A security information and event management system centralizes events from multiple sources, normalizes fields, searches and correlates them, and raises alerts. Collection is not detection by itself. A useful workflow is source and agent setup, transport and trust, parsing, storage, query, detection rule, alert triage, and response. Validate ingestion, time range, field names, indexing delay, and rule schedule before concluding an event is absent.

Example correlation: repeated failed logins (Windows 4625), a successful login (4624), sensitive-file access, then unusual outbound transfer in a short window. This could indicate compromised credentials and possible exfiltration, but is not proof. Investigate user and source identity, expected behavior, file sensitivity, destination, transfer size, endpoint activity, and timing. Tune thresholds and windows to reduce false alerts while maintaining coverage. High volume, false positives, performance, licensing, and maintenance complicate SIEM operation.

Week 43 Honeypots

A honeypot is a deliberately attractive decoy for detecting, diverting, or studying unauthorized activity. Because it should receive little legitimate traffic, a connection can be a useful signal, though scans and misconfiguration can create benign activity. Internal contact may indicate a compromised host, an insider, or accidental traffic; investigate before drawing conclusions.

Low-interaction honeypots emulate limited services and offer lower risk and less detail. High-interaction systems expose more realistic functionality and yield richer behavior but require stronger isolation and monitoring. Cowrie emulates SSH/Telnet interactions and records attempted credentials, commands, and sessions; its level of interaction depends on configuration, so do not assume a real full operating system is always exposed. Honeyd, Dionaea, and T-Pot are other examples from the lecture.

In Lab 6, Cowrie listens on DMZ TCP 2222, and playlog replays a captured terminal session. The lab customizes permitted test accounts and a fake banner, then forwards external TCP 52315 to the DMZ honeypot TCP 2222 with an appropriate WAN rule. Use segmentation, outbound restrictions, logging, and monitoring to limit misuse. A changed SSH host key can be legitimate after rebuilding a lab but can also signal interception: verify the fingerprint through a trusted channel before accepting it. Consider privacy, authorization, and data handling.

Week 44 Traffic monitoring

Packet capture (PCAP) records observed packets; flow records such as NetFlow/IPFIX summarize communication by endpoints, ports, timing, and volume without necessarily retaining payload. Wireshark analyzes captures interactively; tcpdump captures at the command line; Zeek generates protocol and connection logs; Suricata and Snort inspect traffic and generate IDS/IPS alerts. Arkime indexes packet metadata and provides search over stored captures. Collection location, dropped packets, encryption, privacy, and storage all limit visibility.

A capture filter excludes packets from the recorded capture; a Wireshark display filter hides or shows already captured packets without deleting them. Examples: ip.addr == 10.1.0.150, tcp.port == 80, and http.request.method == "POST". Follow TCP or HTTP stream to reconstruct an exchange; export HTTP objects to inspect transferred files when permitted. HTTP form data may be visible as plaintext. Do not assume a capture is complete or that every observed IP is the original user.

TLS lab reasoning

Your quiz identified TLS_RSA_WITH_AES_128_GCM_SHA256 in the supplied capture. In that exercise the supplied server RSA private key could decrypt the recorded session; after decryption the HTTP login and transferred picture were visible. With ephemeral Diffie-Hellman key exchange (for example ECDHE), the server private key alone generally cannot decrypt a recorded session; authorized session secrets such as a client key log may be necessary. RSA in a cipher suite name can refer to authentication rather than key exchange. Analyze only captures and keys you are authorized to access.

The lecture's Mirai example connects default IoT credentials to large-scale scanning and botnet traffic. SolarWinds illustrates suspicious beaconing or unusual outbound destinations from trusted software. Baselines, DNS, connection frequency, traffic volume, and destination context can help identify anomalies, but none alone proves compromise.

Week 46 Proxies and web application firewalls

A forward proxy acts on behalf of clients accessing destinations, supporting outbound policy, logging, caching, and sometimes identity masking. A reverse proxy sits in front of servers, routing inbound requests and potentially providing load balancing, TLS termination, or WAF inspection. A transparent proxy redirects traffic without normal explicit client configuration. These are deployment roles; actual encryption and visibility depend on configuration.

A VPN typically creates an encrypted tunnel for selected traffic, while a proxy often handles selected application traffic and does not inherently encrypt it. Split tunneling means a VPN need not carry all traffic. Neither automatically makes users anonymous. A malicious or misconfigured proxy can collect sensitive data or expose internal resources.

TLS termination at a reverse proxy means the client-proxy connection is encrypted; the proxy-to-backend connection must be separately protected if needed. HTTPS inspection generally requires the client to trust the inspecting CA and raises privacy and trust issues. A WAF such as ModSecurity with OWASP Core Rule Set inspects HTTP requests and responses for patterns such as SQL injection or XSS. Its alerts and blocking rules require tuning, and a WAF does not fix unsafe application code: parameterized queries and proper input handling remain essential.

In Lab 8, Squid logs and blocks test sites, while a reverse proxy and WAF inspect a deliberately vulnerable application. The completed quiz identifies REQUEST-942-APPLICATION-ATTACK-SQLI.conf in the ModSecurity logs. The lab tests detection versus blocking and illustrates false positives and incomplete coverage; adjusting anomaly thresholds can change both legitimate access and security outcomes.

Week 47 IDS and IPS

An intrusion detection system (IDS) observes and alerts; an intrusion prevention system (IPS) can block or drop matching traffic when deployed in a suitable inline enforcement path. A network sensor sees traffic at its observation point; host-based sensors monitor an individual host. Placement affects what is visible. An alert or drop rule is useful only if the traffic traverses the sensor and the engine can inspect it.

Signature detection matches known patterns and depends on current, appropriate rules. Anomaly detection looks for departures from a baseline and may surface novel behavior but can produce noisy alerts. Hybrid approaches combine signals. False positive means benign activity flagged; false negative means malicious activity missed. Encryption, evasion, performance limits, blind spots, stale signatures, and overly broad blocks all matter. Tune and validate rules before enforcing them.

Lab 9 uses Suricata in OPNsense, enabled rule sets, alerts for scanning, ICMP and web traffic, and a custom HTTP rule that matches the text ?cmd=. The rule's action, protocol, source/destination, direction, message, content, case modifier, classification, SID, and revision each serve a role. A text match is a heuristic, not proof of command injection; a different encoding or encrypted payload can evade visibility. The lab changes selected rules from alert to drop and tests both allowed and blocked traffic. An overly broad drop policy can also disrupt legitimate SSH. Check logs, sensor health, selected interface, rule application, and actual traffic before changing policy.

Troubleshooting commands and recovery

Use this as a diagnostic workflow, not as a list of commands to run blindly. The examples use the course lab environment. Replace hostnames, ports, interfaces, paths, and usernames with the values in your exam. Run scans and configuration changes only on authorized systems. A dollar sign is not part of any command here. Read the error and record it before changing anything.

First identify what failed

1. Read the exact error. Note the command, machine, user, time, target address, port, and whether the problem is local or remote. Repeat only a harmless diagnostic if needed.

2. Check spelling, quotation marks, hyphens, spaces, paths, case, and whether you are in Windows CMD, PowerShell, WSL, Rocky Linux, OPNsense, or a container. Linux filenames and commands are case-sensitive. Replace typographic dashes with ordinary hyphens.

3. Test one layer at a time: local command and file, local service, address and route, network and host firewall, application protocol, then authentication or certificate. Check logs at the same time.

4. Make one justified change, test again, and document the result. Back up configuration before changing it. Use sudo only where required; it does not fix incorrect paths or syntax.

General shell and file problems

Where am I, which user am I, and what files are here?

pwd
whoami
id
ls -la

pwd prints the current directory; id shows user and group IDs; ls -la includes hidden entries and permissions. If a relative file path fails, use the correct working directory or an absolute path. Check the file without changing it:

ls -l /path/to/file
file /path/to/file
stat /path/to/file
head -n 30 /path/to/file
tail -n 50 /path/to/file

If the output is long, pipe a text log to less, or search for a term. Press q to leave less. grep -i ignores case and -n shows line numbers.

less /path/to/log
grep -in 'error' /path/to/log
tail -f /path/to/log

Ctrl+C stops tail -f. A permission denied error may mean the file or a parent directory is inaccessible, the command needs an authorized administrator, or SELinux denies access. Inspect ownership and permissions first; do not use chmod 777 or change ownership of a private key as a general fix.

ls -ld /path/to /path/to/file
sudo -l

Command not found: check whether the executable is installed and on PATH. A missing file, an inactive virtual environment, and a typo require different fixes.

command -v nmap
type -a python3
echo "$PATH"
python3 --version

Use man command or command --help for syntax; q exits man. Some programs use a different help flag. If a script exists but cannot run, check its interpreter and permissions. Run only trusted lab scripts.

man ssh
ssh -h
head -n 1 script.sh
ls -l script.sh

First identify the machine and package manager: Rocky uses dnf; Ubuntu/WSL uses apt; OPNsense uses FreeBSD tools. A package that exists on one may have a different name or repository on another. Check network and DNS if repositories cannot be reached. The lab's update and install steps require administrative access.

cat /etc/os-release
df -h
df -i
dnf --version
apt --version

df -h reports filesystem capacity; df -i checks inode exhaustion. A full disk can prevent logs, installs, or container writes. Identify the relevant directory before deleting anything. On Rocky, inspect an installed package and repository availability:

rpm -q httpd

dnf info httpd

On Ubuntu/WSL, check package status and refresh the index if appropriate:

dpkg -s nmap

sudo apt-get update

Read the repository error before retrying. Confirm address, gateway, DNS, reachability, system time, repository configuration, and proxy settings. Do not disable certificate checks as a routine fix.

Network address routing DNS and port checks

On the Linux host, identify interface name, assigned address, and default route:

ip -br addr
ip route
ip route get 10.1.0.150

On Windows CMD, inspect IP, gateway and DNS information:

ipconfig /all
route print

If DHCP did not supply the expected address, verify the correct interface, DHCP scope, gateway, address conflicts, and connection state. In the lab, renew using ipconfig /release followed by ipconfig /renew on the Windows client, or inspect the Linux profile using nmtui. Releasing an address interrupts that connection. DHCP values may differ on another attempt.

Distinguish a DNS failure from an IP connectivity failure. A successful ping tests ICMP reachability, not whether TCP or the application is available. An ICMP failure does not prove that TCP is blocked.

ping -c 4 10.1.0.150
getent hosts www.groupX.com
cat /etc/resolv.conf

Windows alternatives:

ping 10.1.0.150
nslookup www.groupX.com

Check the hosts file when the lab uses a custom DNS name. On Windows it is C:\Windows\System32\drivers\etc\hosts; on Linux it is /etc/hosts. Test the name that matches the certificate, not only the IP address.

Check whether the server is listening locally and whether a client can reach the intended TCP port. On the Linux server:

sudo ss -lntup
sudo ss -lntp | grep ':80'
sudo ss -lntp | grep ':22'

Look at the listening address, port, and process. A service bound only to 127.0.0.1 is not generally reachable remotely. UDP will not appear in the TCP-only command. From Windows PowerShell, test TCP without assuming ping is enabled:

Test-NetConnection 10.1.0.150 -Port 80
Test-NetConnection 10.1.0.150 -Port 22

Interpret the result: connection refused often means the host was reached but no listener accepted the connection, although a firewall may actively reject; a timeout can indicate a dropped packet, routing problem, unavailable host, or return-path issue. Check both ends and logs. For an authorized lab host, a focused service probe can add evidence:

nmap -sV -p 22,80,443,8080 10.1.0.150

TLS certificates and mTLS

Check the name, chain, expiry, intended usage, private key, trust store, and system clock. On the Linux machine:

date -u
openssl x509 -in server.crt -noout -subject -issuer -dates -ext subjectAltName
openssl x509 -in server.crt -noout -text
openssl req -in server.csr -noout -text
openssl verify -CAfile LabCA.crt server.crt

Check the server's presented chain and a name-based HTTPS response. Replace www.groupX.com with the certificate's actual DNS name. The -CAfile option supplies the lab CA for validation; it does not install it globally.

openssl s_client -connect www.groupX.com:443 -servername www.groupX.com -showcerts -CAfile LabCA.crt
curl -v --cacert LabCA.crt https://www.groupX.com/

A self-signed or unknown issuer warning calls for verification and a trusted CA, not automatic bypass. Name mismatch calls for the correct DNS name and matching SAN. An expired or not-yet-valid certificate may require a correct clock or replacement certificate. A chain verification success does not by itself prove a hostname or EKU is correct. If mTLS fails, inspect whether the server requires a client certificate, whether the client has the certificate and matching private key, whether the issuing CA is trusted by the server, and whether client-auth usage and validity are appropriate. Review Apache logs. Do not share private keys.

If local access works but remote access fails, inspect OPNsense and firewalld rules. Check the actual configured log path and filename if the example file is absent. Project etc paths are distinct from the host's /etc. Only restart after identifying and correcting the problem.

Wireshark and TLS capture

If no packets appear, verify the correct capture interface, capture filter, permissions, and whether the traffic actually crosses that interface. A display filter can hide all captured packets: clear it and inspect again. Check time range, endpoints, and TCP stream; packet loss or a short capture may prevent reconstruction.

If TLS decryption fails, verify the negotiated cipher suite, the correct capture and matching key or authorized session key log, and whether the handshake was captured. The RSA server private key from the exercise works only for compatible RSA key exchange. An ECDHE session generally needs its session secrets; the server's long-term private key alone is insufficient. Do not assume missing plaintext means there was no application traffic.

Squid reverse proxy and Suricata

For Squid, verify client/proxy settings, OPNsense rules and redirects, proxy service health, access logs, destination DNS, and the test site's protocol. A blocked site should produce a relevant log entry; if HTTPS inspection is used, check trusted CA and certificate name. If a reverse proxy fails, inspect its container logs and configuration, backend listener, backend address/port and network path. An HTTP 502 or 504 is a reason to inspect the upstream, not proof of one specific failure.

Exam troubleshooting answer template

State: (1) symptom and environment; (2) one diagnostic command or GUI log and expected output; (3) likely causes supported by the result; (4) the smallest authorized correction; and (5) a retest. Example: HTTPS times out remotely but curl localhost succeeds. Check the 443 listener and OPNsense/firewalld logs from the remote test, correct the missing authorized pass rule if confirmed, then retry the same HTTPS request and verify logs. Practice questions

Try answering these aloud or on paper. They are generated from course objectives and quiz patterns, not leaked exam content.

1 What does a firewall do and why use a DMZ

It enforces traffic policy at network boundaries. A DMZ separates externally reachable services from the internal LAN, allowing only required paths and reducing exposure.

2 Compare stateless and stateful filtering

Stateless filtering evaluates packets individually; stateful filtering tracks connection context and can recognize return traffic of an allowed flow.

3 An allow rule for TCP 80 works but ping fails Is that contradictory

No. Ping commonly uses ICMP, a different protocol. Check ICMP rules, the host firewall, and route.

4 Explain WAN IP port 52314 to 10 1 0 150 port 22

The firewall translates the destination to the DMZ host and TCP 22. The WAN rule, routing, host firewall, and an SSH service listening on 22 must permit the connection.

5 Why can SSH pass through a rule for TCP 8080

A port-based rule sees TCP 8080, not necessarily the application. SSH can listen on that port; application-aware inspection may identify the protocol.

6 What is the difference between CVE and CVSS

CVE identifies a disclosed vulnerability; CVSS expresses severity characteristics as a score. Neither alone proves a particular host is affected or compromised.

7 A scanner reports an old PHP version What next

Validate the service and version, configuration, and vendor advisory; consider backported fixes and exposure. Prioritize and remediate based on actual risk, then rescan.

8 What do Docker mappings 8010 to 80 and 8022 to 22 imply

The host exposes container HTTP on 8010 and container SSH on 8022 in this lab. Verify using service detection because port numbers alone are not proof.

9 Describe three complementary ways to find vulnerabilities

Combine automated scanning of deployed systems, static source review, and dynamic or fuzz testing. Add dependency inventory and authorized manual testing.

10 What are the three Zero Trust principles in the slides

Verify explicitly; use least privilege; assume breach. Controls include MFA, segmentation, device assessment, and continuous monitoring.

11 Match Logjam POODLE and CCS injection to the quiz CVEs

Logjam: CVE-2015-4000; POODLE: CVE-2014-3566; CCS injection: CVE-2014-0224.

12 A server is reachable from LAN but not externally Name four checks

Check WAN destination and port, NAT translation, WAN filtering, routing and return path, host firewall, and service listener. Inspect logs and test from the actual outside source.

13 How does an SBOM help vulnerability management

It lists software components and versions, helping identify affected dependencies when advisories appear. It must be kept accurate and paired with applicability checks.

14 What did the lab teach about broad scanning rules

Allow only the necessary authorized scan window and target, verify availability, then remove temporary access and vulnerable containers after the exercise.

15 What lesson connects Equifax and SolarWinds

Both require knowing deployed software, but Equifax emphasizes timely patching of a known flaw while SolarWinds highlights trust and security of the software supply chain.

More practice questions for Weeks 38 to 47

16 What does a CA sign and what stays private

The CA signs a certificate that binds an identity to a public key. The subject retains its private key. A CSR contains the public key and identity information and is signed to prove possession of the private key.

17 A certificate is signed by your internal CA but the browser warns Why

Check whether that CA is trusted by this browser or system, whether intermediates are available, whether the SAN matches the requested name, validity, intended purpose, and revocation or policy failures. A signed certificate is not automatically trusted.

18 What changes with mutual TLS

The client validates the server certificate and the server also requests and validates a client certificate. The client must possess the matching private key and be trusted under the server's policy.

19 Compare Windows events 4688 and 4663

4688 records process creation when enabled. 4663 reports an object access attempt under the relevant audit policy and object audit settings. Examine process, account, object, outcome, and time.

20 How do you make a useful investigation timeline

Synchronize clocks; preserve time zone and original records; combine host, authentication, network, and application events by time, identity, and source. Note missing events and ingestion delays.

21 What is normalization in a SIEM and why use it

It maps different source formats into consistent fields, so events can be searched and correlated across systems. It may lose detail if incorrectly parsed, so preserve original evidence where practical.

22 Several failed logins precede success and file access What does this prove

It is a suspicious pattern, not proof of an attack. Correlate by account and host within a time window, then check user behavior, source, endpoint and transfer evidence before deciding.

23 Why is a honeypot connection useful and what is its risk

Unexpected interaction can reveal scanning or compromise and provide behavioral evidence. A realistic honeypot can be abused as a stepping stone unless isolated, monitored, and restricted.

24 Compare capture and display filters in Wireshark

A capture filter prevents nonmatching packets from being recorded; a display filter hides nonmatching packets already captured. The latter can be changed while reviewing a capture.

25 Can a captured HTTPS session always be decrypted with the server private key

No. The supplied lab uses a compatible RSA key exchange, but ephemeral key exchange such as ECDHE provides forward secrecy against later server-key disclosure. Authorized session secrets may be required.

26 Forward proxy or reverse proxy

A forward proxy serves client outbound requests and can apply organization policy. A reverse proxy fronts backend servers and can route requests, terminate TLS, load-balance, and apply a WAF.

27 Why can a WAF block SQL injection but not eliminate the underlying flaw

The WAF matches traffic patterns and can miss variants or block legitimate requests. Safe parameterized queries, application fixes, least privilege, and testing address the underlying risk.

28 Compare IDS and IPS

IDS detects and alerts; IPS can actively block traffic when deployed with an enforcement path. Both require suitable visibility and tuned detection rules.

29 Explain false positive and false negative

A false positive flags benign behavior as malicious. A false negative misses malicious behavior. Tightening a rule can reduce one while increasing the other, so validate against realistic traffic.

30 A Suricata drop rule appears enabled but traffic still passes What do you check

Check sensor interface and placement, inline IPS mode, rule and policy action, reload/application, protocol and direction, encryption, match conditions, logs, and whether traffic actually crosses the sensor.

31 Trace a combined incident from network to endpoint

Start with a network alert, record source, destination and time, correlate firewall and SIEM records, identify the endpoint and process, examine authentication and file events, and assess whether data left. Preserve evidence and distinguish observations from hypotheses.

32 How do you prioritize a scanner finding

Confirm the actual asset, component and configuration, compare vendor guidance and fixes, assess exploitability, exposure and business impact, remediate, and verify. A CVE or severity score is only part of the decision.
